Pages take four seconds, rankings are sliding, and the last developer said it was the hosting. It usually isn't. I diagnose the actual cause and give you the fix in writing before any work starts.

Specialism

Elementor,
built the way
it should be.

Most of my work is Elementor — and most Elementor sites are slow. That isn't the tool's fault. It's containers nested five levels deep, six addon packs loaded to render two widgets, and a page that ships three megabytes before a single image appears.

I build the other way. Same editor your team already knows, none of the weight that usually comes with it.

The target on every build

Green Core Web Vitals on mobile — the benchmark most Elementor sites never reach, and the one Google actually ranks on. Measured on real hardware before handover, not on a desktop connection.

How

No addon stacking

A single custom widget written in PHP instead of a third-party pack that loads 300KB of CSS and JS to render one element.

Flat container structure

Layouts built two levels deep, not five. Fewer DOM nodes means faster paint and a layout that doesn't collapse on mobile.

CSS in the stylesheet

Spacing, animation and responsive behaviour handled in real CSS rather than widget settings that inject inline styles per element.

Conditional asset loading

Elementor's own scripts, icon libraries and web fonts load only on pages that use them — self-hosted, never called from a third party.

Queries under control

Custom loops in place of widget-based post queries that fire unindexed database calls on every page load.

Editable without breaking

Locked structure, open content. Your team edits text and images freely and cannot accidentally dismantle the layout.
