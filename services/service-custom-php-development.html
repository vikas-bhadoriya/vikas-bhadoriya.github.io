What this actually is

Three shapes
of the same work.

Custom PHP is a vague heading, so here's what it means in practice. Almost every request falls into one of three shapes, and the shape determines the cost far more than the feature list.

Two systems that don't talk

WordPress and a CRM, an ERP, an accounting package, a booking system. Data has to move, in one or both directions, without someone re-typing it every morning.

Logic your business runs on

Pricing that depends on six variables, an eligibility check, a multi-step approval, a quote calculator. Rules that exist in someone's head or a spreadsheet and need to exist in code.

Work a person does by hand

Exporting a report every Monday, reconciling two lists, sending the same email after every order. Four hours a week is two hundred a year, which is usually more than automating it costs.

How it's written

Six things
that stop this
becoming a liability.

Custom code is only an asset if someone else can maintain it. Bad custom code is worse than no custom code — it works until it doesn't, and then nobody understands why.

  • In the right place, not the theme

    Functionality goes in a plugin, not functions.php. The most common mistake I inherit is business logic written into a theme, which means changing the design means rewriting the business.

  • WordPress standards, not personal style

    Hook naming, file structure, sanitisation and escaping conventions as the WordPress community writes them. Any competent developer opens it and recognises the shape immediately.

  • Security assumed hostile

    Every input sanitised, every output escaped, prepared statements for every query, nonces on every form, capability checks on every action. Custom code is where most WordPress breaches start.

  • Failure handled, not ignored

    What happens when the API is down, the file is malformed, the payment times out. Errors logged with enough context to debug, retries where sensible, and a fallback that doesn't lose data.

  • Built to scale past today's data

    Code that works on 100 records and dies on 100,000 is common. Queries indexed, batches chunked, long operations backgrounded rather than run in a page request that times out.

  • Documented for whoever inherits it

    Comments explaining decisions rather than restating the code, a README covering what it does and how to configure it, and a plain-language note for the non-developer who'll one day ask what this is.

How it runs

Scope

What I
won't write.

Mostly because it would be a bad investment for you, and in two cases because it's a bad idea for anyone.

  • Anything editing WordPress core. There is always another way, and the next update erases it.
  • Business logic in the theme. If the current site has it there, moving it out is usually the first recommendation.
  • Scrapers or anything breaching a service's terms. Including for internal use only.
  • Standalone PHP applications. If it doesn't need WordPress, it shouldn't be in WordPress — and a Laravel developer will build it better.
  • A workaround for a broken plugin. Fixing or replacing the plugin is cheaper than maintaining a patch on top of it.

Questions

Asked before
committing.

Custom code is a longer-term commitment than a plugin subscription, and the concerns are usually about year three rather than launch.

Is custom code a liability for us long-term?

It can be, and that's a fair concern. Badly written custom code is genuinely worse than no custom code — it works until it doesn't, and then nobody knows why.

What makes it an asset instead: WordPress coding standards, everything in a plugin rather than the theme, documented, in Git. Another developer picks it up from the README rather than from a conversation with me.

Should this be custom code or a plugin from the repository?

Use the plugin if one fits — I'll tell you which. Custom becomes right when nothing does it, when you'd need three plugins to cover one requirement, or when the requirement is specific to how your business works and always will be.

Integrations and business logic are almost always custom, because nobody else has your exact process.

Can you work on code someone else wrote?

Yes, and a fair amount of my work is exactly that. It's hourly rather than fixed, because reading unfamiliar code is the slow part and estimating it accurately before reading it isn't possible.

A short paid review first tells you what state it's in and roughly what the work costs, before you commit further.

What PHP versions do you support?

PHP 8 by default, written to remain compatible with 7.4 where a client's hosting still requires it. If you're on anything older than 7.4 that's a security issue in itself and worth addressing before anything else — it's no longer receiving fixes.

Will it survive WordPress updates?

Yes, because it uses documented APIs and hooks rather than undocumented internals, and never edits core. WordPress takes backwards compatibility seriously.

What does break is code depending on another plugin's internals. Where an integration requires that, I'll flag the risk rather than let it surprise you.

Can you automate something we currently do manually?

Often, and it's usually the easiest ROI to justify. Four hours a week is roughly two hundred hours a year — most automations of that size pay for themselves within a few months.

Worth saying: occasionally the honest answer is that the process itself should change rather than be automated. You'd hear that too.
