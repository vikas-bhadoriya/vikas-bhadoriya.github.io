Why this goes wrong

Three ways a
Figma handoff fails.

A design file is a static picture of one screen width. Everything that isn't in it — hover states, what happens at 380px, how the layout behaves with twice the copy — is a decision someone makes during the build. Usually badly.

It's "close enough"

Spacing drifts by a few pixels everywhere, type sizes get rounded, the type scale collapses into three sizes instead of six. Nothing is individually wrong and the whole thing looks cheaper than the design.

It's slow

Four addon packs installed to get one hover effect, containers nested five deep, every icon library loaded on every page. The design was fine — the build shipped three megabytes.

The client breaks it

Editing is left wide open, someone changes a heading, and a section collapses. Then every content change becomes a support ticket, which is your problem rather than theirs.

What you get

Seven things,
every time.

Not a feature list — this is what's in scope on every build at every price point, including the parts that usually get quoted as extras.

  • Pixel-accurate at every breakpoint

    Spacing, type scale, colour and states match the file. Where the design only specifies desktop, I'll propose the tablet and mobile behaviour and get it signed off before building — rather than inventing it silently.

  • A real design system, not ad-hoc values

    Your type scale, colour palette and spacing become Elementor global settings. Change a brand colour once and it updates everywhere, instead of hunting through forty widgets.

  • Custom widgets instead of addon packs

    If the design needs something Elementor doesn't do, I write a widget in PHP. One purpose-built widget rather than a 300KB addon pack loaded on every page to render one element.

  • Performance built in, not bolted on

    Flat container structure, conditional asset loading, self-hosted fonts, images in modern formats with explicit dimensions. Green Core Web Vitals on mobile is the target on every build.

  • A locked editing layer

    Structure fixed, content open. The team edits text, images and links freely and cannot accidentally dismantle a section. This is the single biggest reduction in your post-launch support load.

  • Every state the file didn't show

    Hover, focus, active, disabled, loading, empty and error states. Long-content overflow. What a form looks like after submission. All the things a static mockup never includes.

  • Accessible by default

    Semantic structure, keyboard operability, visible focus rings, labelled form fields, contrast checked against the palette. If something in the design fails contrast, you hear about it before the build, not after.

Questions

Asked before
every project.

If yours isn't here, send the file — the review is free and answers most of these for your specific case.

How exact is "pixel-accurate"?

At the breakpoints the design specifies, spacing and type match the file. Between them, the layout scales on the system I build from your type scale and spacing values rather than jumping between fixed states.

Where a design can't work as drawn — text that overflows at 380px, a three-column grid with no mobile version — you get that in the file review before quoting, with a proposed solution rather than a silent decision.

Do you work from XD, PSD or Sketch too?

Yes, all of them, at the same rates. Figma is easiest because inspect mode gives exact values, but XD and Sketch are fine. Flat PSDs take slightly longer since spacing has to be measured rather than read, and layer organisation matters more.

Why Elementor rather than a custom theme?

It depends entirely on who maintains the site. If your client's marketing person needs to rearrange a page next quarter, Elementor is right — built properly, the performance difference is small. If nobody will ever touch the layout, a custom theme is leaner and I'd say so.

The tool follows the maintainer, not the other way round. How I build in Elementor.

Won't Elementor make the site slow?

Most Elementor sites are slow, and that's a build problem rather than a tool problem — containers nested five deep, six addon packs loaded to render two widgets, everything loading on every page.

Built flat, with custom PHP widgets instead of addon packs and conditional asset loading, green Core Web Vitals on mobile is achievable. That's the target on every build, measured on real hardware before handover.

What do you need from us to start?

The design file with view access, final copy or a plan for it, image assets at full resolution, and either hosting access or permission to set up staging. If fonts are licensed, the licence needs to cover web use — I'll check and flag it if not.

Can you work white-label for our agency?

Yes — NDA before the first call, no contact with your client, work in your repository under your brand, invoiced to you. There's a non-solicit clause in the contract. Rates, capacity and terms.

What if we don't like how it turns out?

Two revision rounds per page are included, and you're watching a staging link throughout — so problems get caught at page two rather than at handover. If the build genuinely doesn't match the file, fixing it isn't a revision round, it's a defect and it's on me.

How long does a typical site take?

Two to three weeks for six pages, one week for a landing page, four weeks or so for a larger site with several templates. The variable is almost always feedback speed on your side, so the quote names who owes what and when.
