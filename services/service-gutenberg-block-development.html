Why teams struggle

Three problems
with core blocks alone.

Core blocks are good primitives. The trouble starts when every page becomes an exercise in assembling primitives correctly, over and over, by people whose job isn't layout.

Every page is built slightly differently

Five people build the same section five ways. Spacing drifts, heading levels wander, the mobile version breaks on the one that used columns instead of a group.

Editors can break the design

Full styling controls on every block means anyone can set purple text at 60px. Either the design erodes quietly, or someone spends their week reverting changes.

Content isn't structured data

A testimonial assembled from generic blocks is just markup. As a proper block it has an author, a role and a quote — queryable, reusable, and exportable if you ever move.

What you get

Six things,
every block.

Built against the current block API with block.json registration, so they behave like core blocks rather than something bolted alongside the editor.

  • Fields, not freeform styling

    The block asks for exactly what the content needs — headline, image, three stats — and offers only the controls that should vary. Nothing to get wrong, because the wrong options aren't there.

  • Editing that looks like the front end

    The block renders in the editor as it will on the page, not as a grey placeholder saying "Testimonial Block". Editors see what they're making, which is the entire promise of the block editor.

  • Locked to your design system

    Colour, spacing and type pulled from your theme.json palette rather than free-entry values. A brand change updates every instance instead of requiring a hunt through pages.

  • Dynamic where it should be

    Static blocks save markup into the post; dynamic blocks render at request time and stay current. Anything pulling from post types, ACF fields or an API is dynamic, so updating the source updates every page.

  • Accessible markup by default

    Correct heading levels, keyboard operability, focus states, and images that require alt text rather than treating it as optional. Interactive blocks — accordions, tabs — are where this usually gets skipped.

  • Delivered as a plugin you own

    Packaged separately from the theme so it survives a redesign, documented, in Git. No licence, no per-site fee, reusable across your sites.

Two ways to build

React blocks
or ACF blocks.

Both are legitimate and I'll recommend based on what the block does, not on which is more fashionable. The difference matters mostly for who maintains it afterwards.

OPTION A

ACF Blocks — usually the right choice

Rendered in PHP with fields defined in ACF. Faster to build, far cheaper to maintain, and any WordPress developer can extend them without a JavaScript build step. Suits the great majority of content blocks, and it's what I recommend by default.

OPTION B

Native React blocks — when the editing needs it

Built with the block API in JavaScript. Worth the extra cost when the block needs rich in-editor interaction, InnerBlocks nesting, or when you're shipping to a client who requires no ACF dependency. More expensive to build and to maintain.

HONESTLY

Where my limit is

My React is working knowledge rather than specialism. Straightforward native blocks are fine; a deeply interactive editor experience is better built by a React specialist, and I'd tell you that rather than take it on.

Questions

Asked before
committing.

Mostly about whether custom blocks are worth it when core blocks are free.

Can't we just use core blocks and patterns?

Often yes, and block patterns are underrated — a locked pattern built from core blocks solves a lot of this for nothing. Start there.

Custom blocks earn their cost when the content has real structure worth capturing, when editors keep building the same thing inconsistently, or when the pattern needs dynamic data. If a pattern would do, I'll say so.

ACF blocks or native React blocks?

ACF blocks for most content, and it isn't a compromise — they're faster to build, cheaper to maintain, and any WordPress developer can extend them without a build step.

Native React blocks when the editing experience itself needs interaction, or when a client requires no ACF dependency. They cost more to build and more to maintain, so the reason should be specific.

Will these work with our existing theme?

Yes. Blocks ship as a plugin rather than living in the theme, so they survive a redesign. They inherit colour and typography from your theme.json where one exists, or use their own values where it doesn't.

What happens if a block changes later?

Dynamic blocks re-render on every page load, so a change applies everywhere immediately. Static blocks save their markup into the post, so changing the structure needs a deprecation path to avoid the editor flagging existing content as invalid.

That's a real maintenance consideration, and it's a reason most blocks I build are dynamic.

Can editors still control the styling?

As much as you want, and the right amount is usually less than the default. Typically each block exposes a few chosen variations — alignment, a colour from the palette, a background option — rather than the full styling panel.

You decide where the line is. That decision is part of the spec rather than an afterthought.

Should we be using the block editor at all?

If your team is already comfortable in it, yes — custom blocks make it substantially better. If they're on Elementor and content with it, switching is a large change for uncertain benefit and I wouldn't push it.

The block editor is where WordPress is heading, but "eventually" is not a reason to migrate a working site this quarter.
