When headless
is a mistake.

Headless is oversold, and it is the wrong answer more often than the people selling it admit. Three cases where a normal WordPress site is genuinely better, and I'd rather say so before you commit a budget.

Nobody owns the frontend

Headless means two codebases and two deployment pipelines. Without a frontend developer on your side or on retainer, you've turned a site anyone can maintain into one only a specialist can touch.

You want it for speed

A well-built WordPress site with proper caching is fast. Headless can be faster, but the gap is smaller than the pitch suggests and the cost is roughly double. Fix the build first — see speed optimisation.

Your editors need to see the page

Live preview across a decoupled frontend is solvable but genuinely fiddly. If your team relies on seeing changes before publishing, that friction shows up every single day.

When it's right

Six things
the WordPress side
has to get right.

Where the case does hold, the WordPress half is what makes it work or fail. Most failed headless projects failed here rather than in the frontend.

  • A content model designed for consumption, not display

    In a theme you can paper over a weak structure in the template. Through an API you can't — the frontend receives exactly what the model gives it. Content types, fields and relationships are designed as data first.

  • A deliberate API surface

    The default REST output is verbose and leaks internals. Custom endpoints or a shaped GraphQL schema return what the frontend needs and nothing else, with sensible pagination and consistent field naming.

  • Advanced Custom Fields, exposed properly

    ACF is the backbone of most headless builds. Field groups modelled for the frontend, exposed to REST or GraphQL, with flexible content and repeaters that serialise into something predictable rather than a nested mess.

  • Authentication that's actually secure

    Application passwords, JWT or OAuth depending on the consumer. Capability checks on every endpoint, rate limiting, and no write endpoint exposed that shouldn't be. Public read APIs are the common place this goes wrong.

  • Preview and revalidation that work

    Draft preview against the decoupled frontend, and webhooks to trigger rebuilds or cache invalidation on publish. This is the part most headless builds skip, and the part editors complain about within a fortnight.

  • An editing experience that survives decoupling

    Editors lose the visual context a theme gave them. That's replaced with clear field labels, helper text, image guidance and validation, so publishing doesn't become guesswork.

Scope

Where my part
stops.

Being precise about this matters more here than anywhere else, because a decoupled project has two halves and an unclear boundary is where they fail.

  • I don't build the frontend. React and Next.js are your team's or another contractor's. I've worked alongside both and will spec the API to whatever they need.
  • Not frontend performance or SEO. Server rendering, metadata and Core Web Vitals on a decoupled frontend belong to whoever owns it.
  • Not hosting the frontend. Vercel, Netlify or your own infrastructure — configured by your team.
  • Not a migration to a different CMS. If the conclusion is that WordPress isn't right, I'll say so, but moving you to Contentful isn't my work.
  • Not GraphQL server development from scratch. WPGraphQL where GraphQL is wanted; a bespoke server is a different project.

Questions

Asked before
committing.

Headless decisions are hard to reverse, so these are worth resolving before anyone writes code.

Do we actually need headless?

Probably not, and I'd rather say that than take the project. It's genuinely right when you have a frontend team who want their own stack, when the same content feeds several destinations — site, app, kiosk, partner — or when you're integrating WordPress into an existing application.

It's usually wrong when the reason is "headless is faster" or "headless is modern". Both are half-true and neither justifies doubling the maintenance surface.

Can you build the React or Next.js frontend too?

No, and I'd rather be straight about that than take work I'd be second-best at. My React is working knowledge, not specialism.

What I do well is the WordPress half — content model, API design, authentication, preview and the editing experience. I've worked alongside frontend teams on decoupled builds and will spec the API to whatever shape they want.

REST or GraphQL?

Depends on the frontend team's preference and how varied the queries are. REST is simpler, cacheable at the edge, and fine when the frontend needs a predictable set of things. WPGraphQL is better when the frontend needs to compose queries and you'd otherwise build a dozen bespoke endpoints.

I'll build either. If your team has no strong preference, REST with well-designed endpoints is usually less to maintain.

Will our editors still be able to preview?

Yes, but it's real work rather than a checkbox — draft previews have to be routed to the decoupled frontend with authentication. It's included in a full backend build and quoted explicitly, because the projects that skip it are the ones editors complain about.

Is the API secure by default?

No. WordPress exposes a fair amount over REST out of the box, including user data on some configurations. Locking that down — capability checks, disabling unnecessary endpoints, authentication on anything that isn't genuinely public, rate limiting — is part of every API build rather than an extra.

Can we go headless later rather than now?

Yes, and it's often the sensible sequence. A clean content model and a solid ACF structure are useful on a conventional WordPress site and are most of the groundwork for decoupling later.

Build the content model well now, run a normal theme on it, and decouple when there's an actual reason. That's cheaper than committing to two codebases before you need them.
