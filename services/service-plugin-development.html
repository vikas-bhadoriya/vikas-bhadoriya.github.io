When custom is right

Three situations
worth the money.

Custom isn't always the answer — a well-maintained plugin that does the job is cheaper and I'll say so. These are the cases where it isn't.

Nothing does it

The requirement is specific to how your business works. Integrating with the system you already run, processing your data your way, or a workflow nobody else has.

Four plugins are covering one job

Each was added to patch a gap. Together they conflict, slow the site down, and nobody can safely remove any of them. Consolidating usually costs less than two years of the current arrangement.

You're paying for 5% of a plugin

A $300-a-year subscription for one feature, with the other ninety loading on every page. Rebuilding just the part you use often pays for itself inside two renewal cycles.

How it's built

Seven things
that make it
maintainable.

Custom code is only cheaper than a subscription if someone else can pick it up later. These are the decisions that make that true.

  • WordPress coding standards, not my preferences

    Written the way the WordPress community writes plugins — hook naming, file structure, sanitisation and escaping conventions. Any competent WordPress developer opens it and recognises the shape immediately.

  • Update-safe by construction

    No core files edited, no theme files depended on, no assumptions about the current WordPress version that will break at the next release. It survives updates because it never fought them.

  • Security as the default posture

    Every input sanitised, every output escaped, nonces on every form and AJAX call, capability checks on every action, prepared statements for every query. Plugins are the most common attack surface on a WordPress site.

  • An admin interface your team can use

    Settings built with the WordPress Settings API so they look and behave like the rest of the dashboard, rather than a bespoke panel that needs its own explanation.

  • Loads only where it's needed

    Assets enqueued conditionally, admin code not loaded on the front end, heavy operations deferred. A plugin that runs on every page load when it's needed on two is a performance problem you'll pay for later.

  • Extensible by whoever comes next

    Your own action and filter hooks so future changes don't require editing the plugin itself. That's the difference between code someone can build on and code they'll eventually replace.

  • Documented properly

    Inline comments explaining decisions rather than restating the code, a README covering installation, settings and hooks, and a plain-language note on what it does for whoever inherits it.

How it runs

Five stages.

The first stage is the one that saves money. Half of what people ask for turns out to be solvable more cheaply another way.

STAGE 01

Is this the answer?

Whether an existing plugin already does it, whether it's really a settings problem, whether custom is worth it. Free, and sometimes it ends here.

STAGE 02

Written spec

What it does, what it explicitly doesn't, where it appears in the admin, and how it behaves at the edges. Fixed price against that.

STAGE 03

Build

In Git from the first commit, on staging. Core functionality first so you can try the real thing early rather than approve a description.

STAGE 04

Test the edges

Empty states, bad input, permission failures, what happens when the third-party API is down. The parts that only surface in production otherwise.

STAGE 05

Handover

Repository, documentation, a recorded walkthrough, and 30 days of bug fixes at no charge.

Scope

What I
won't build.

Mostly things that would be a bad investment for you, and one that would be a bad idea for anyone.

  • A plugin that already exists and works. If a well-maintained plugin does the job, use it. I'll tell you which one.
  • Anything requiring core file edits. There's always another way, and core edits are wiped by the next update.
  • Plugins for public distribution. Building for the WordPress.org repository means supporting thousands of unknown configurations — a different job with a different cost.
  • Scrapers or anything that violates a service's terms. Including "just for internal use".
  • A plugin to work around a broken theme. That's treating a symptom. Fix the theme.

Questions

Asked before
committing.

Custom code is a bigger commitment than a subscription, and the concerns are usually about what happens afterwards.

Isn't a $99 plugin cheaper than custom development?

Usually, and when it is I'll tell you which one to buy. The maths changes when the subscription is annual, when you need three plugins to cover one requirement, or when the plugin does ninety things and loads all of them on every page.

A $300-a-year subscription is $1,500 over five years, before counting the performance cost and the risk of the author abandoning it.

What if you disappear? Who maintains it?

Anyone competent with WordPress. That's the reason for the coding standards, the documentation and the Git history — the code is written to be handed over, not to keep you dependent.

No proprietary framework, no obfuscation, no licence key phoning home. You own it outright and could put it on the open market tomorrow.

Will it break when WordPress updates?

It shouldn't, because it uses documented APIs and hooks rather than undocumented internals. WordPress takes backwards compatibility unusually seriously — plugins written properly a decade ago often still run.

What does break things is depending on another plugin's internals, or on a specific theme. Both are avoided by design.

Can you extend a plugin we already have?

Often, yes — most decent plugins provide hooks for exactly this, and extending is cheaper than replacing. What I won't do is edit the plugin's own files, since the next update erases the work.

If it offers no hooks at all, that's a signal the plugin was built carelessly and worth discussing.

Do you write tests?

For plugins handling money, data integrity or anything with real consequences, yes — unit tests on the logic that matters. For a small display plugin, no, because the test suite would cost more than the plugin and give you little.

The spec says which applies, so it's a decision rather than an omission.

Can it be used across multiple sites?

Yes. You own the code and there's no per-site licensing. Agencies frequently commission a plugin once and deploy it for several clients — that's an expected use, not a loophole.
